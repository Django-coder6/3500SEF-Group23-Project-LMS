## Trigger policy and acceptance checks

The later `R10_docker-smoke.md` instruction supersedes the job-only condition
in `R10_W04-task.md`: workflow pushes are limited to `main` and `develop`;
PRs targeting either branch still run all five jobs. Both Docker timeout
settings and all smoke steps remain unchanged.

| Event | Expected CI after this patch |
|---|---|
| Push to main or develop | Full workflow |
| Push to a working branch without a PR | No CI |
| Push to a working branch with a PR to main/develop | PR synchronization runs CI; no additional push run |
| PR opened, synchronized or reopened against main/develop | Full workflow |
| PR targeting another working branch | No CI from this workflow |

The trade-off applies to every job, including backend, frontend and commitlint.
A contributor without hooks is checked when a qualifying PR is opened or updated,
but receives no automated checks on an isolated branch push. Open the PR promptly.

- [ ] After approved publication, confirm one PR-event run and no feature-push run
      for the same update; all five jobs, including docker-smoke, must pass.
- [ ] After reviewed merge, confirm a successful develop push run at the merge SHA.
- [ ] Before tagging, require all dependency gates above and all five jobs to pass
      on the final candidate; download its fresh coverage artifact.
- [ ] Verify intake, storage, pickup verification and handover against the real
      stack, including duplicate and concurrent handover rejection.
- [ ] Obtain the required non-author review and R1's release decision. Check that
      v0.2.0 is still absent, and record the exact release SHA and release notes.
